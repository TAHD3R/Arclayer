# i18n Standards and Practices (CelestialCMS)

This document defines the organization, namespace strategy, and development workflow for i18n. The goal is to:

* **Predictability**: Ensure every new string has a clear location, naming convention, and validation path.
* **Maintainability**: Prevent `common.json` from becoming a "dumping ground" for unrelated strings.
* **AI/LLM Efficiency**: Modularize files to reduce token consumption and improve context accuracy when collaborating with AI.

> **Scope**: This document primarily covers the **Admin Dashboard (`apps/web/admin`)**, global locales, and backend error code mapping.


## 1. Directory Structure

### 1.1 Core System Locales

System-level strings are maintained at the repository root:

```text
locales/
  zh-CN/                   # Source of Truth
    common.json
    nav.json
    settings.json
    errors.json            # Backend Error Mappings
    ...
  en-US/
    ... (Mirrored files)

```

### 1.2 Plugin Locales

Plugin-specific strings are stored within the plugin directory and merged at runtime:
`plugins/<plugin_id>/locales/<locale>/*.json`


## 2. Namespace Strategy

### 2.1 Why Use Namespaces?

* **Decoupling**: Smaller files lead to fewer merge conflicts and easier code reviews.
* **Domain Ownership**: A key’s prefix and file location immediately signal its function.
* **Performance**: Sets the foundation for lazy-loading language resources by route.

### 2.2 Core Namespace Registry

| Namespace | File | Key Prefix | Description |
| --- | --- | --- | --- |
| **`common`** | `common.json` | `ACTION_*`, `STATUS_*` | Truly global strings (e.g., Save, Cancel, Success). |
| **`nav`** | `nav.json` | `NAV_*` | Sidebar, breadcrumbs, and top menus. |
| **`settings`** | `settings.json` | `SET_*` | General settings, Storage, SEO, etc. |
| **`auth`** | `auth.json` | `AUTH_*` | Login, Reset Password, and Permissions. |
| **`assets`** | `assets.json` | `ASSET_*` | Media library and asset management. |
| **`errors`** | `errors.json` | `ERR_*` | Mapping backend error codes to user-friendly tips. |


## 3. Naming Conventions

We enforce the `UPPER_SNAKE_CASE` style with mandatory **domain prefixes**.

1. **Prefix Requirement**: Every key must start with its namespace shorthand (e.g., `SET_STORAGE_TITLE`).
2. **Semantic Clarity**: Avoid generic keys like `TITLE`, `OK`, or `TEXT1`.
3. **No Duplication**: Search globally (`rg`) before adding a new key to see if a synonym already exists.
4. **Interpolation**: Use `{{variable}}` syntax for dynamic content. Do not concatenate strings in code.


## 4. Development Workflow

### 4.1 Adding New Strings

1. **Identify Namespace**: Choose the correct `.json` file based on the feature area.
2. **Synchronize**: Add the key to **both** `zh-CN` and `en-US` simultaneously.
3. **Implementation**:
```tsx
// Usage within a component
const { t } = useTranslation("settings");
return <Button>{t("SET_SAVE_CHANGES")}</Button>;

// Cross-namespace usage
t("common:ACTION_CONFIRM");

```



### 4.2 Error Handling Logic

The backend should return stable error codes (e.g., `INSUFFICIENT_PERMISSIONS`). The frontend maps these in `errors.json`:

```json
// errors.json
{
  "INSUFFICIENT_PERMISSIONS": "You do not have permission to perform this action."
}

```


## 5. Frontend Integration (Admin Web)

When adding a **new namespace file**, you must register it in:
`apps/web/admin/src/utils/i18n/resources.ts`

1. **Import** the new JSON files.
2. Add the namespace to the `I18N_NAMESPACES` type/enum.
3. Assign the resource to the `i18nResources` object.


## 6. Best Practices & Pitfalls

* **Don't Bloat `common**`: If a string is only used in one module, it doesn't belong in `common`.
* **Prefer Value Updates over Key Changes**: Changing a key requires a global search-and-replace; changing a value is isolated.
* **Use `Trans` for Rich Text**: Use the `<Trans />` component from `react-i18next` when you need to embed components (like links) inside a translated string.
