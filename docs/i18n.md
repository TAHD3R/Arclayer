# i18n 规范与实践（CelestialCMS）

本文档用于统一 i18n 的组织方式、命名空间拆分策略与开发流程，目标是：

- 让“新增文案”变得可预测：知道放哪、怎么命名、怎么校验
- 让文件保持可维护：避免一个 `common.json` 越来越大、越来越难找
- 让 AI/LLM 协作成本更低：按功能拆分后，定位问题时无需反复读取超大 JSON（节省 token）

> 约定：本文档以“后台管理端（apps/web/admin）+ 全局 locales”作为主要场景；后端错误码映射也在此统一说明。

---

## 1. 目录结构（基线）

系统级文案统一维护在仓库根目录：

```
locales/
  zh-CN/
    common.json
    nav.json
    setup.json
    settings.json
    account.json
    notifications.json
    command.json
    assets.json
    auth.json
    errors.json
    plugin.json
  en-US/
    ... 同名文件
```

插件自带文案放在插件目录内（系统会自动合并）：

```
plugins/<plugin_id>/locales/<locale>/*.json
```

## 2. 命名空间（namespace）策略

### 2.1 为什么要拆 namespace

拆 namespace 的价值不是“形式主义”，而是为了：

- 降低单文件体积（更容易 review、定位、冲突更少）
- 建立“职责边界”：一个 key 从名字和文件就能看出归属
- 为未来的按需加载（lazy load / route-level namespaces）留出空间

### 2.2 当前命名空间清单（建议不要随意改名）

| namespace       | 文件                 | 典型 key 前缀          | 说明                             |
| --------------- | -------------------- | ---------------------- | -------------------------------- |
| `common`        | `common.json`        | `REQUEST_*`、`BACK` 等 | 真正跨模块通用的少量文案         |
| `nav`           | `nav.json`           | `NAV_*`                | 后台导航/菜单                    |
| `setup`         | `setup.json`         | `SETUP_*`              | 初始化向导                       |
| `settings`      | `settings.json`      | `SETTINGS_*`           | 设置页（通用设置、存储、SEO 等） |
| `account`       | `account.json`       | `ACCOUNT_*`            | 账号菜单/个人设置入口            |
| `notifications` | `notifications.json` | `NOTIFICATIONS_*`      | 通知中心、通知列表               |
| `command`       | `command.json`       | `CMDK_*`               | Command-K/命令面板               |
| `assets`        | `assets.json`        | `ASSET_*`              | 资源库                           |
| `errors`        | `errors.json`        | `BAD_REQUEST` 等       | 错误码 -> 用户提示               |
| `auth`          | `auth.json`          | `LOGIN_SUCCESS` 等     | 鉴权/登录/重置密码               |
| `plugin`        | `plugin.json`        | `PLUGIN_*`             | 插件管理通用提示                 |

> 原则：新增 key 时不要默认放 `common`，先问自己“它属于哪个模块/页面/功能域？”。

## 3. Key 命名规范

当前项目延续 `UPPER_SNAKE_CASE` 风格，并依赖“前缀”标识归属（如 `SETTINGS_*`）。

强制规则：

1. 新增 key 必须能从名字判断归属：必须包含领域前缀（例如：`SETTINGS_STORAGE_*`）。
2. 禁止使用无语义的 key：`TITLE`、`OK`、`TEXT1` 这类会导致冲突和难以检索。
3. 同一语义不要重复造轮子：新增前先全局搜索（`rg`）是否已有同义 key。
4. 同一 namespace 内禁止“同 key 不同语义”。

## 4. 新增/修改文案的开发流程（推荐 Checklist）

### 4.1 新增词条（最常见）

1. 确定归属 namespace（如设置页 -> `settings`）。
2. 在 `locales/zh-CN/<ns>.json` 与 `locales/en-US/<ns>.json` 同时添加同名 key。
3. 前端使用：

````tsx
import { useTranslation } from \"react-i18next\";\n\nconst { t } = useTranslation(\"settings\");\n\n<Button>{t(\"SETTINGS_SAVE\")}</Button>\n```

跨 namespace 时显式指定：

```ts
t(\"common:REQUEST_FAILED\");\n```

4. 自检：两种语言 key 是否一致、是否遗漏。

### 4.2 修改现有词条

- 优先“改 value 不改 key”（避免全局重构）。
- 若必须改 key：
  - 先全局搜索使用点并一并修改
  - 同步更新两种语言文件
  - 避免“一个 PR 里顺手大规模改名”（极易引入遗漏）

## 5. 与前端 i18next 资源加载的关系

后台管理端的资源入口（仅供理解，不建议随意改动）：

- `apps/web/admin/src/utils/i18n/resources.ts`
  - 负责 import 各 namespace 的 JSON
  - 定义 `I18N_NAMESPACES`

当你新增一个新的 namespace 文件时，需要同步：

1. 添加 import
2. 把 namespace 加入 `I18N_NAMESPACES`
3. 把资源挂到 `i18nResources[locale][namespace]`

## 6. 后端错误码与前端展示（推荐约定）

目标：后端返回“稳定的错误码”，前端/多语言由 `errors.json` 决定显示文本。

建议：

- 错误码使用稳定的 `SCREAMING_SNAKE_CASE`（例如：`ADMIN_RBAC_PROVIDER_UNAVAILABLE`）
- 前端 toast 或错误提示时：优先 `t(errorCode, { ns: \"errors\" })`
- i18next 的缺省行为：找不到 key 时会返回 key 本身；业务层可将其视为“未翻译”，再降级为通用提示（如 `common:REQUEST_FAILED`）

---

## 7. 常见坑与最佳实践

1. 不要把页面级文案塞 `common`
   - 经验：`common` 一旦变大，维护成本指数级上涨
2. 不要在代码里拼接句子（尤其是带变量、复数、不同语序的）
   - 用 i18n 的插值：`{{name}}` / `{name}`（以项目实际用法为准）
3. `Trans` 用于富文本或需要嵌入组件的场景
4. 每个 PR 最好把“新增 key”控制在合理规模，避免 review 失焦

---

## 8. 迁移说明

为了修复“所有文案堆 common”的历史问题，本仓库已在 2026-01-29 将原 `common.json` 按职责拆分为多个 namespace 文件（`nav/setup/settings/...`），并同步更新前端使用点与资源加载入口。

后续新增文案请遵循本规范，避免回退到单文件堆叠模式。
