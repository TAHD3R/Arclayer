# i18n Standards and Practices (CelestialCMS)

This document defines the target i18n architecture and workflow for CelestialCMS.
It is a normative guideline for frontend Admin, backend localization behavior, and plugin locale integration.

## 1. Goals

- Keep translation ownership explicit and predictable.
- Keep namespace growth maintainable and reviewable.
- Keep backend error localization and frontend copy localization consistent.
- Avoid key drift, duplicate strings, and interpolation bugs.

## 2. Scope

This guideline applies to:

- Global locale resources in `locales/<locale>/*.json`
- Admin/Studio frontend i18n integration (`apps/admin/src/lib/i18n/*`, `apps/studio/src/lib/i18n/*`)
- Backend localization runtime (`apps/api/src/core/i18n.py`, locale middleware, error mapping)
- Plugin locale resources (`plugins/<plugin_id>/locales/<locale>/*.json`)

Current runtime locales:

- `zh-CN` (default)
- `en-US`

## 3. Locale Sources and Merge Rules

### 3.1 Core locales (system source)

Core locale files are stored at repository root:

```text
locales/
  zh-CN/
  en-US/
```

These files are the base resources used by both frontend and backend.

### 3.2 Plugin locales

Plugin-specific resources are stored at:

```text
plugins/<plugin_id>/locales/<locale>/*.json
```

Plugin locale paths are registered by plugin discovery and merged into backend i18n runtime.

### 3.3 Backend merge precedence

Backend i18n loader merges locale paths in registration order.

- Core locales are loaded first.
- Plugin locale paths are registered afterward.
- For the same `namespace + key`, later loaded data overrides earlier values.

Do not reuse core namespace keys in plugins unless intentional override is required and documented.

## 4. Namespace Governance

### 4.1 Namespace registry (current core set)

Current core namespaces include (not limited to):

- `common`
- `nav`
- `rbac`
- `setup`
- `invite`
- `team`
- `debug`
- `activity`
- `content_pages`
- `appearance`
- `settings`
- `account`
- `notifications`
- `command`
- `assets`
- `errors`
- `auth`
- `plugin`

### 4.2 Namespace split rules

- Use existing namespace first whenever ownership is clear.
- Create a new namespace only when a feature introduces a stable language domain.
- `common` is for truly cross-domain text only, not convenience dumping.
- `errors` is reserved for backend error-code mapping.

## 5. Key Naming and Interpolation Rules

### 5.1 Key style

- `UPPER_SNAKE_CASE` is mandatory.
- Domain prefixes (for example `SET_`, `AUTH_`, `ASSET_`) are recommended, not mandatory.
- Keys must be semantic and stable; avoid generic keys like `TITLE`, `TEXT1`, `OK`.

### 5.2 Interpolation policy

Interpolation syntax depends on runtime:

- Frontend (`react-i18next`): use `{{variable}}`
- Backend `t(namespace, key, **kwargs)` (`format_map`): use `{variable}`

Do not mix interpolation syntaxes for keys intended for backend runtime formatting.

## 6. Frontend (Admin/Studio) Integration Contract

### 6.1 Resource registration

When adding a new core namespace file, register it in:

- `apps/admin/src/lib/i18n/resources.ts`
- `apps/studio/src/lib/i18n/resources.ts` (Studio)

Required updates:

1. Import both locale JSON files (`zh-CN` and `en-US`).
2. Add namespace to `I18N_NAMESPACES`.
3. Add namespace resources to `i18nResources` for both locales.

### 6.2 Usage rules

- Use `useTranslation(namespace)` in components/routes.
- Use explicit namespace prefixes for cross-namespace calls (`t("common:ACTION_CONFIRM")`).
- Do not hardcode user-facing text in JSX/TSX.
- Do not concatenate translated fragments in code.

## 7. Backend Localization Contract

### 7.1 Locale resolution order

Request locale resolution follows this priority:

1. `X-Locale` header
2. `lang` query parameter
3. Workspace default locale (when request is workspace scoped)
4. System default locale
5. `Accept-Language` (only when no explicit/default locale)
6. `zh-CN` fallback

### 7.2 Error localization contract

- Backend should return stable error codes.
- Frontend maps user-facing error text via `locales/<locale>/errors.json`.
- New public error codes must include both `zh-CN` and `en-US` mappings.

### 7.3 Backend i18n references

For i18n references persisted in DB/config (for example menu or plugin manifest refs), use:

- `namespace:key` format (for example `nav:NAV_DASHBOARD`)

## 8. Plugin Localization Contract

- Plugin locales must live under plugin directories (not in root `locales/`).
- Plugin keys should use plugin-owned namespace files (for example `oauth_social.json`).
- Avoid key collisions with core namespaces unless explicitly overriding by design.
- In development watch mode, locale file changes trigger i18n cache clear behavior (no full restart required for locale-only changes).

## 9. Standard Workflow

When adding or changing localized text:

1. Select the namespace by ownership.
2. Search existing keys before adding new ones (`rg` across `locales/`).
3. Add/update both `zh-CN` and `en-US` in the same change.
4. If new namespace is introduced, register it in Admin i18n resources.
5. Implement calls using `t(...)` / `useTranslation(...)` (no hardcoded UI copy).
6. Verify affected pages/API errors under both locales.

## 10. PR Review Checklist

- [ ] Namespace ownership is correct (no `common` dumping).
- [ ] `zh-CN` and `en-US` are synchronized.
- [ ] Key naming follows `UPPER_SNAKE_CASE` and semantic clarity.
- [ ] Interpolation syntax matches runtime usage.
- [ ] New namespace is registered in `apps/admin/src/lib/i18n/resources.ts`.
- [ ] Backend error code additions include `errors.json` mapping.
- [ ] Plugin locale changes are scoped to plugin locale directories.

## 11. Anti-Patterns

- Putting module-specific text into `common`.
- Changing stable keys without migration rationale.
- Reusing one key for different semantics in different screens.
- Hardcoded strings in components/routes.
- Mixing `{{var}}` and `{var}` in the wrong runtime path.
