# Platform Identity & Access Contract

Status: Approved domain contract
Parent: [Platform Control Plane Productization Rollout](./admin-control-plane-rollout.md)
Experience authority: [Product and Platform administration experience redesign](./product-admin-experience-redesign.md)

## 1. Scope

This contract defines one Identity & Access Platform Domain for deployment-wide sign-in policy, identity providers, Platform team authority, Platform Roles and Permissions, mandatory multi-factor authentication, and Platform Session operations.

“Identity & Access” is the canonical architecture term. The primary product label is localized as “访问与安全” / “Access & Security”; pages and actions use task language rather than repeating the domain name or exposing internal authorization vocabulary.

## 3. Information architecture

Identity & Access opens the **Platform team** queue by default and contains these peer operational surfaces:

1. **Platform team**: Instance Owner, invited and active Platform Operators, role assignments, MFA readiness, recent access, and explicit revoke or recovery actions.
2. **Roles & permissions**: localized Built-in Platform Roles, deployment-owned Custom Platform Roles, readable permission descriptions, affected operators, copy-to-custom workflows, change preview, and audited assignments.
3. **Sign-in & registration**: public-registration availability, email requirements and verification, allowed email domains, automatic-account-provisioning policy, and installed identity-provider configuration.

Current-actor MFA methods and device-scoped Platform Sessions are not peer administration pages. They live in the account settings overlay opened from the Sidebar user menu, alongside the current identity profile and local appearance/language preferences. The overlay uses the same server-enforced MFA and Session contracts; moving the surface does not weaken permission, Step-up, expiry, revocation, or Audit requirements.

The domain has no decorative Overview. Configuration readiness and security problems appear beside the affected work queue and project an Operational Signal when operator action is required.

## 4. Authority boundaries

- Identity & Access owns deployment authentication policy and Platform Console authority; it does not grant Workspace membership or permissions.
- Workspaces retains ordinary User investigation and individual account actions, including authorized password, linked-login, 2FA, Session, disable, and recovery workflows. Access & Security does not create a second User directory.
- Workspace Administration retains Workspace members, invitations, roles, and permissions. A Workspace administrator never becomes a Platform Operator through tenant authority.
- Extensibility may own installation and trust lifecycle for an identity-provider Connector, while Identity & Access exclusively owns whether and how that provider participates in sign-in.
- The Product API may return only a minimal `Platform Entry Eligibility` projection for the current identity. It is discoverability metadata for the Product Application account menu, not evidence that a Platform Session exists and not an authorization input to any Platform API endpoint.
- Opening the configured Platform Host transfers no Product Session, access token, Workspace context, Platform Role, or Platform Permission. The Platform Host independently verifies the identity, current Instance Owner or Platform Operator status, mandatory MFA, and an independently issued or validated Platform Session before the Platform API evaluates the exact permission for each request.
- A Platform Operator Invitation records intended roles but grants no effective Platform Role, Platform Permission, Platform Session, or Platform Entry Eligibility. Only the intended identity may accept it, and active Platform Operator status plus the intended role assignments become effective atomically only after explicit acceptance and mandatory MFA enrollment complete.
- The Instance Owner and an active Platform Operator with the exact invitation permission may create an invitation. The server authorizes the union of the intended roles against the inviter's Delegable Platform Authority; UI visibility, possession of a team-management page, or assignability of each role in isolation cannot authorize a broader combination.
- Delegable Platform Authority excludes Instance Owner transfer and any other explicitly non-delegable authority. An operator cannot use invitations to grant authority outside the server-defined envelope, even when the target role is valid or the operator personally holds authority that is not delegable.
- Platform Operators receive Platform Permissions only through one or more Platform Role assignments. Their effective delegated permissions are the additive union of those roles; direct per-operator grants, denies, and overrides do not exist.
- Built-in Platform Roles are Arclayer-managed and immutable in the Console. A deployment may copy one into an independent Custom Platform Role or create a Custom Platform Role directly, but it cannot edit the built-in source or turn the Instance Owner into an assignable role.
- Expiry, revocation, identity mismatch, failed MFA enrollment, or concurrent invalidation leaves the invitation ineffective and creates no partial operator authority. Instance Owner transfer remains a separate non-delegable workflow rather than an invitation side effect.
- Every Platform team, role, permission, MFA, and session mutation is authorized by an exact Platform Permission or non-delegable Instance Owner authority and writes canonical Platform Audit evidence.

### 4.1 Platform Operator invitation lifecycle

1. An authorized invitation request identifies one intended human identity, revision-bound intended Platform Roles, the inviter, and an explicit expiry. The server requires Instance Owner authority or the exact invitation permission and validates the combined roles against the inviter's Delegable Platform Authority. Sending records intent and Audit evidence; it does not create an active operator or effective role assignment.
2. Before acceptance, the Platform team queue presents the invitation as waiting for the recipient, with understandable role consequences, inviter, sent time, expiry, and an available revoke action. It shows only roles the current actor may assign and never presents the recipient as an active team member or MFA-compliant operator.
3. The intended identity authenticates through the configured identity authority, explicitly accepts the invitation, and completes mandatory MFA enrollment. If any intended role contains a permission whose trusted action contract requires phishing-resistant verification, acceptance also requires a verified security key or passkey before activation. The server then revalidates the inviter's active status and invitation permission, every intended role revision and verification requirement, the combined Delegable Platform Authority, and the invitation itself before atomically activating the Platform Operator with those role assignments.
4. If any prerequisite is no longer valid, activation fails visibly and leaves both operator status and role assignments unchanged. The invitation cannot produce a Platform Session until activation succeeds.
5. Activation, expiry, revocation, and failed acceptance attempts retain canonical Audit evidence without recording credentials, MFA secrets, invitation secrets, or authentication payloads.

### 4.2 Platform Role model

1. Arclayer ships a deliberately small Built-in Platform Role catalog for common operational responsibilities. Each role has a stable identity, localized name and outcome-oriented description, explicit Platform Permissions, and a server revision; it is not editable, deletable, or assignable as Instance Owner authority.
2. Copying a Built-in Platform Role snapshots its current permissions into a new Custom Platform Role with an independent identity and lifecycle. Later changes to either role never mutate the other implicitly.
3. Authorized operators may create Custom Platform Roles for deployment-specific responsibilities. User-authored role names and descriptions remain verbatim, while permission labels and consequences come from the bilingual Platform permission catalog.
4. A Platform Operator may hold multiple Built-in and Custom Platform Roles. Effective permissions are their additive, deduplicated union, and every Platform API request still checks the exact required permission rather than trusting a role name.
5. No direct grant, direct deny, one-person override, hidden default role, or automatic role inferred from Workspace membership exists. A permission difference requires an explicit reusable Custom Platform Role and audited role assignment.
6. The Instance Owner appears in the Platform team with clear ownership status, but no synthetic all-access role row, editable assignment, copy action, or role API represents its authority.

### 4.3 Custom Platform Role change semantics

1. Editing a Custom Platform Role creates a draft against its current server revision and changes no effective authority. The review step requests a server-generated, revision-bound preview rather than deriving impact from frontend state.
2. The preview shows added and removed permission responsibilities, affected Platform Operators, affected Platform Domains and Capabilities, the current actor's own access impact, and pending Platform Operator Invitations bound to the current role revision. It uses localized task language first and reserves raw permission codes for authorized diagnostic detail.
3. Apply requires the expected current role revision, exact role-change permission, Delegable Platform Authority for every newly added permission, and explicit confirmation. A stale revision, changed assignment, lost actor authority, or changed permission catalog rejects the apply and requires a new preview.
4. A successful apply atomically creates the next Platform Role Revision and makes it current for every existing assignment. Assignments never store permission snapshots, and no operator receives only part of the new permission set.
5. Existing Platform Sessions remain authenticated, but they confer no cached authorization snapshot. Old permission-cache entries and permission projections become unusable before apply success is acknowledged, and every subsequent Platform API request evaluates the current union of assigned role revisions.
6. Pending invitations bound to the replaced revision become invalid with explicit product copy and require a newly reviewed invitation. The system never silently updates an invitation to the changed role.
7. The role change records canonical Audit evidence for actor, expected and committed revisions, safe permission diff, affected-operator count, invalidated-invitation count, result, and correlation identity without copying secrets or unrelated operator data.

### 4.4 Permission removal and accepted operations

1. Permission removal, role unassignment, operator deactivation, and Platform Session revocation immediately deny every new Platform API command that requires the removed authority, including confirmation, retry, cancellation, scope expansion, approval, and a later human-authorized workflow step.
2. An Accepted Platform Operation is a committed durable operation with captured original actor, exact action permission, Platform Role revisions, scope/preview identity, idempotency identity, acceptance time, and Audit correlation. This evidence explains why work was accepted; it is not reusable authority for another command.
3. Later authority loss does not automatically cancel, roll back, pause, or relabel the accepted operation. Its background phases continue according to the owning Platform Domain's committed execution, partial-result, external-effect, recovery, and terminal-state contract.
4. The owning domain may expose cancellation only when it defines a safe boundary, exact cancellation permission, idempotency, already-committed effects, per-item or phase consequences, terminal result, and Audit evidence. A currently authorized actor must issue that distinct cancellation command; the original actor's former authority is insufficient.
5. Deferred confirmations, approvals, retries, failed-item replays, increased scope, and recovery choices are new commands and always resolve current Platform authority. A worker cannot use captured acceptance evidence to invent a missing human decision or widen the original operation.
6. Role-change and operator-removal impact previews show recognizable active Accepted Platform Operations, owning domains, current phases, and whether a safe cancellation action exists. They explain that permission removal blocks new interaction but does not promise to recall committed effects.
7. Completion and cancellation evidence retain both the original accepting actor and any later cancelling or recovery actor. Partial or irreversible outcomes remain explicit and are never collapsed into a generic cancelled or successful state.

### 4.5 Platform Operator offboarding

1. Ordinary offboarding uses a high-risk “Remove platform access” workflow and never hard-deletes the shared identity or Platform actor history. Its server preview shows current roles, effective responsibilities, active Platform Sessions, pending invitations sent by or addressed to the operator, active Accepted Platform Operations, and the consequences for new access.
2. Apply requires the exact current authority, an expected operator revision, explicit confirmation, and a reason. Before success is acknowledged, one server-authoritative revocation barrier makes Platform Entry Eligibility false, revokes every Platform Session, ends every effective role assignment, removes Delegable Platform Authority, and invalidates the affected pending invitations.
3. Ended assignments, invitation history, role revisions, past sessions, Audit attribution, and Accepted Platform Operations remain linked to the Deactivated Platform Operator. Primary team views separate active members from “Access removed” history without making historical actors anonymous or presenting them as current members.
4. Offboarding does not disable the underlying Product identity, terminate Product Sessions, change Workspace or Organization membership, remove tenant roles, or alter customer-owned content. Those authorities retain their own lifecycle and exact permissions.
5. Accepted Platform Operations continue only under section 4.4. The former operator cannot confirm, retry, cancel, recover, expand, or otherwise interact with them; any later action is attributed to a currently authorized actor.
6. A Deactivated Platform Operator has no reversible pause state, retained effective role assignment, reusable Platform Session, or one-click restore. Returning requires a new identity-bound invitation, current role and Delegable Platform Authority checks, mandatory MFA satisfaction, atomic activation, and a newly issued Platform Session.
7. The Instance Owner is not a Platform Operator removal target. Ownership must be transferred through the separate non-delegable ownership workflow before the former owner can enter any later operator lifecycle.
8. Routine offboarding never deletes Audit or actor records. A legally required identity-erasure process remains separate from access removal and must preserve required evidence semantics without inventing anonymous historical actions.

### 4.6 Instance Ownership Transfer

1. Only the current Instance Owner may nominate a target. The target must be a distinct active Platform Operator with current MFA readiness; an invitation, Deactivated Platform Operator, ordinary Product User, Workspace administrator, or external email address is not eligible.
2. Nomination requests a server-generated, revision-bound preview showing the target identity and current roles, verified phishing-resistant-method readiness, non-delegable ownership responsibilities, active Accepted Platform Operations for both principals, affected pending invitations, both principals' active Platform Sessions, and the exact Built-in or Custom Platform Roles the former owner will retain after transfer. Selecting no former-owner roles means removal of their Platform access.
3. Nomination changes no authority. The current owner remains the only Instance Owner, the target remains a Platform Operator, and neither receives a transitional or shared-owner capability while acceptance is pending.
4. The target opens the canonical transfer workflow, completes fresh Phishing-resistant Platform Verification with a verified security key or passkey, reviews the same consequences and former-owner outcome, and explicitly accepts. Possession of a Product Session, invitation link, existing operator Session, or authenticator-app code alone cannot accept ownership.
5. Acceptance revalidates the current owner, target active status, expected ownership and operator revisions, target MFA challenge, selected former-owner role revisions, current permission catalog, and affected invitation/delegation state. Any drift fails without changing either principal and requires a new preview.
6. One transaction preserves the exactly-one-owner invariant: the target's effective operator assignments end, the target becomes Instance Owner, the former owner loses ownership, and the former owner either becomes an active Platform Operator with only the reviewed roles or becomes a Deactivated Platform Operator. No observer or API request can see zero or two owners.
7. Before success is acknowledged, every existing Platform Session for both principals is revoked. The new owner establishes ownership-bound Platform access after commit; a retained former operator establishes a new Platform Session whose authority comes only from the selected roles. Product Sessions remain unchanged.
8. Pending invitations or Delegable Platform Authority created by the former owner are revalidated against the post-transfer roles; anything no longer authorized becomes explicitly invalid. Accepted Platform Operations retain their original actor and evidence and continue only within their committed scope.
9. Audit records nomination, target acceptance, MFA verification result without secret material, expected and committed revisions, former-owner outcome, role changes, Session revocations, affected invitations, exact ownership transition, and correlation identity. A failed transfer records no successful ownership change.

### 4.7 Instance Ownership Recovery

1. Ownership Recovery is a deployment-configured break-glass authority outside Platform Console navigation and ordinary Platform APIs. Production enablement requires one verified recovery path: self-hosted deployments provision offline recovery material or an infrastructure-custodied procedure, while managed deployments provision a reviewed support recovery process with named control ownership.
2. Platform Operators cannot request approval through role quorum, vote themselves into ownership, use team-management permission as recovery proof, or convert an existing Platform Session into Owner authority. Recovery custodians and support personnel can evaluate recovery evidence but cannot browse customer data, enter the Console as the Owner, or receive a normal Platform Session from that authority.
3. A recovery request verifies deployment identity, current ownership revision, recovery proof, intended human identity, reason, and recovery outcome. It enters the configured notification and hold policy, not an immediate owner mutation; the current Owner and verified recovery contacts receive customer-safe notices when reachable, and the visible deadline and next step use deployment policy rather than a hidden hard-coded delay.
4. If the same human Owner proves identity after losing Platform MFA access, the recovery preserves the Owner principal, revokes all existing Platform Sessions and superseded recovery material, requires a verified security key or passkey under current Platform MFA policy, and issues no new Platform Session until those requirements succeed. It does not create an ownership transfer or Operator role.
5. If the Owner is unavailable and replacement is approved, the target identity completes required verification and enrolls and verifies a security key or passkey before commit. One transaction preserves exactly one Owner, deactivates the former Owner for Platform access, ends any target Operator role assignments when present, revokes both identities' Platform Sessions, revalidates affected invitations, and makes no support or recovery custodian the Owner.
6. Accepted Platform Operations retain original attribution and continue under section 4.4. Recovery evidence cannot retry, cancel, approve, widen, or recover those operations; every later command uses the restored or replacement Owner's new Platform Session.
7. Before success, the recovery proof, hold completion, notifications, target identity, target MFA, current ownership revision, and deployment recovery policy are revalidated. Failure leaves ownership and Platform authority unchanged, exposes the exact recovery state, and never falls through to an Operator promotion.
8. A successful recovery consumes or rotates the used recovery material according to its deployment contract, revokes obsolete recovery sessions, and records tamper-evident evidence for proof class, reviewers or infrastructure executor, notifications, hold, target verification, old/new Owner identity, Session revocations, result, and correlation identity without storing raw secrets or identity documents in general Audit payloads.
9. The recovery surface uses a separate trust boundary, rate limiting, abuse monitoring, safe diagnostics, and an operational runbook. Its availability and evidence store are monitored independently from the ordinary Console so a Console outage cannot silently disable the declared recovery path.

### 4.8 Step-up Platform Verification

1. The trusted action capability contract, not the frontend, declares whether a Platform API mutation requires step-up and whether that step-up requires phishing-resistant assurance. The classification records the reason, accepted method assurance, and versioned freshness policy and is limited to consequences that justify another factor challenge; ordinary reads, routine investigation, low-risk explicit saves, and background refresh never require repeated MFA merely because they occur in the Console.
2. Phishing-resistant required classes initially include Instance Ownership Transfer, deployment sign-in or identity-provider authority changes, Platform privilege elevation or delegation, administrative Platform MFA reset, critical credential replacement, and any later owning-domain action whose documented blast radius justifies the stronger method. Instance Ownership Recovery keeps its separate out-of-Console proof and is not converted into a step-up action, but the restored or replacement Owner must verify a security key or passkey before receiving a Platform Session.
3. The operator first reviews the canonical revision-bound impact preview. At final apply, the Platform Host obtains a method that satisfies the action's current assurance requirement and the server binds the proof and verified assurance to actor, Platform Session, exact action capability and permission, target and scope, expected preview/target/catalog revisions, idempotency identity, and the action's freshness policy.
4. Step-up proves recent identity confirmation only. The final Platform API call independently revalidates current Instance Owner or Platform Operator status, exact Platform Permission, Delegable Platform Authority where applicable, action capability, preview, target revision, prerequisites, idempotency, and current policy.
5. Session revocation, operator deactivation, permission loss, role revision change, freshness expiry, action-policy or assurance revision, target/preview/catalog drift, or scope change invalidates the proof with explicit product copy. The UI never silently requests a different scope, downgrades the action or required method, substitutes TOTP for a phishing-resistant requirement, or treats a prior login challenge as fresh verification.
6. A network retry may reuse the proof only for the same idempotency identity and unchanged action context while it remains valid; it cannot authorize a second operation. Once an Accepted Platform Operation commits, its captured verification result is evidence for that scope, while retry, cancellation, approval, recovery choice, or expansion remains a new currently authorized command and requires step-up when its own action class declares it.
7. The step-up overlay preserves the reviewed context, names the exact plain-language action and affected scope, supports keyboard and accessible MFA interaction, and returns to an unchanged review on failure. It does not expose factor internals, proof tokens, policy codes, or raw authentication errors.
8. Audit records actor, action capability, target/scope summary, preview and policy revisions, verification result, apply result, idempotency and correlation identities, and safe failure category without recording factors, proof values, credentials, or authentication payloads.

### 4.9 Device-scoped Platform Session lifecycle

1. Each browser or device establishes a separately identifiable Platform Session after the required Platform MFA challenge. Product Sessions, Product cookies or tokens, Workspace context, and another device's Platform Session cannot create, upgrade, or substitute for it.
2. Every Platform Session records its actor, opaque session identity, created time, recent activity time, inactivity deadline, absolute deadline, policy revision, and revocation or expiry result. Device presentation uses a safe user-recognizable label and never exposes bearer material, raw fingerprints, credential data, or authentication payloads.
3. A versioned Platform Session Lifecycle Policy defines both the inactivity timeout and absolute maximum lifetime. Qualifying activity may move the inactivity deadline forward only up to the absolute deadline; refresh or token rotation cannot extend the Session beyond that deadline or silently create a replacement Session.
4. The current Instance Owner or Platform Operator can inspect their devices, creation time, recent activity, expiry, and current-device marker. They may revoke one Platform Session or revoke every other Platform Session; revoking the current Session completes sign-out only after the server-authoritative revocation succeeds.
5. An authorized security operator may inspect or revoke another Platform actor's Sessions only through the exact action-scoped Platform Permission and canonical Audit path. Self-service Session revocation does not imply team-management, role, identity-provider, Workspace, or Product-session authority.
6. Inactivity expiry, absolute expiry, explicit revocation, operator deactivation, ownership transfer, and ownership recovery deny every subsequent Platform API request from the affected Session. Every Step-up Platform Verification bound to it becomes unusable at the same boundary.
7. An expired or revoked Session cannot be resumed. Creating a new Platform Session follows the current Platform sign-in and MFA policy; absolute expiry always requires a new MFA-backed Platform sign-in rather than refresh continuation.
8. Concrete inactivity and absolute durations come from the versioned security policy and are not hard-coded in this product contract. The model imposes no arbitrary concurrent-Session count limit; if a future security or operational requirement justifies one, it requires an explicit policy, product consequence, and migration decision.

### 4.10 Platform Operator MFA recovery

1. Successful initial Platform MFA setup produces a new set of high-entropy, single-use recovery codes. The codes are displayed once for the operator to store, retained only through a non-reversible verifier, never sent through Communications, and never exposed later to the Instance Owner, another Platform Operator, support personnel, Audit, or diagnostics.
2. An operator who can still satisfy current Platform MFA may regenerate the recovery-code set through a self-service Step-up Platform Verification. Regeneration atomically invalidates every prior unused code; the UI never claims that an old and new set are both valid.
3. A non-owner operator who loses their factors first authenticates through the current configured identity authority and submits one recovery code. A valid code authorizes only the bounded Platform MFA Recovery flow: before new enrollment begins, the used code and remaining code set become unusable and all existing Platform Sessions and bound Step-up proofs are revoked.
4. Recovery-code verification does not create a Platform Session, grant a Platform Permission, expose the Console, or reactivate a Deactivated Platform Operator. The same identity must enroll and verify new MFA credentials under current policy before the server issues a new recovery-code set and a new Platform Session authorized from current role revisions.
5. When no valid recovery code remains, the Instance Owner or an active Platform Operator with the exact action-scoped MFA-reset permission may start recovery for another active non-owner operator. The initiator reviews the target identity, active Sessions, current roles, accepted-operation consequence, and recovery result, then completes Phishing-resistant Platform Verification before apply.
6. Apply revalidates both actors, target active status and revision, initiator authority, step-up proof, and idempotency. One revocation barrier invalidates every target Platform Session, Step-up proof, enrolled Platform MFA credential, and recovery code and moves the target into an MFA-setup-required state; accepted operations retain their original evidence and continue under section 4.4.
7. The MFA-setup-required state preserves active Platform Role assignments and Product identity but makes Platform authority unusable. Only identity verification, new MFA enrollment and verification, and sign-out are available; no temporary Session, bypass factor, grace period, reduced-permission Console, or administrator-selected credential exists.
8. After successful enrollment, the target receives a new recovery-code set and may establish a new Platform Session under current roles. Failure, abandonment, expiry, identity mismatch, or concurrent offboarding leaves Platform access blocked and never restores an old factor, code, proof, or Session.
9. The Instance Owner cannot be targeted by operator MFA reset. Loss of Owner MFA follows the separate Instance Ownership Recovery contract, preserving its out-of-Console custody, review, notification, exactly-one-owner, and Session-revocation invariants.
10. Recovery-code attempts and administrative resets are abuse-monitored and record safe Audit evidence for actor, target, method class, revisions, Session revocations, enrollment completion, result, and correlation identity without recording codes, factors, identity proofs, or authentication payloads.

### 4.11 Platform MFA methods

1. The initial Platform MFA method catalog contains two method classes: user-verifying WebAuthn security keys or passkeys as the preferred phishing-resistant method, and standards-based time-based one-time passwords from an authenticator app as the compatibility method. Email links, email codes, SMS codes, voice calls, recovery codes, and Product Sessions are not Platform MFA methods.
2. The Instance Owner and each Platform Operator may enroll multiple verified methods across both supported classes. Platform MFA readiness requires at least one currently verified method; the platform does not designate one irreplaceable primary credential or collapse several credentials into one shared device record.
3. WebAuthn enrollment and challenge use a server-generated single-use challenge bound to the configured Platform origin and relying-party identity and require user verification. The server retains only the credential's public verification material and safe operational metadata; private key material, biometric data, platform-authenticator secrets, and full browser fingerprints never reach or remain in Arclayer.
4. A WebAuthn method may be a hardware security key or a device/platform passkey, including a synchronized passkey when the client authenticator satisfies current user-verification policy. Hardware attestation is not required unless a later explicit deployment security policy documents the compatibility and enrollment consequences.
5. Authenticator-app enrollment displays the TOTP secret only during setup, stores it encrypted at rest, and activates the method only after the operator submits a valid generated code. The secret is never returned later, placed in a URL, written to Audit or diagnostics, or delivered through Communications.
6. After activation, adding a method, regenerating recovery codes, or removing a method requires action-bound Step-up Platform Verification and current Session authority. Removing a security key or passkey requires phishing-resistant verification with another verified WebAuthn method when the actor's ownership or roles require one. A method can be renamed with a safe user-authored label, but method class, verification state, credential identity, and security evidence are server-owned.
7. The last verified method cannot be removed. The Instance Owner and any Operator whose roles contain a phishing-resistant action also cannot remove their last verified security key or passkey. Replacement verifies the new required-strength method before atomically retiring the old one; failure leaves the existing method and readiness unchanged rather than producing an MFA-less or assurance-ineligible active actor.
8. Initial invitation acceptance and Platform MFA Recovery may enroll a method without an existing Platform factor only inside their identity-bound, no-authority bootstrap flows. No normal Console or Platform API authority becomes available until a supported method is verified and the surrounding activation or recovery transaction succeeds.
9. After identity authentication, an MFA challenge lists the operator's safe recognizable method labels and lets them choose any currently usable enrolled method. Before identity authentication, the surface does not disclose whether an identity has a passkey, security key, authenticator app, recovery codes, or Platform access.
10. Recovery codes remain single-use recovery material under section 4.10 and never appear as a routine Platform MFA or Step-up method. Losing every enrolled method follows Platform MFA Recovery for a non-owner Operator or Instance Ownership Recovery for the Owner.
11. Enrollment, challenge, rename, replacement, removal, verification failure, and method-policy changes produce safe Audit and security evidence without recording WebAuthn challenges, TOTP secrets or codes, recovery codes, private material, biometric data, or authentication payloads.

### 4.12 Phishing-resistant verification requirements

1. The trusted Platform action and permission catalog derives one server-authoritative verification requirement for each action: baseline Step-up Platform Verification or Phishing-resistant Platform Verification. Roles, invitations, navigation, previews, and the frontend consume that requirement and cannot redefine, weaken, or infer it from labels or form fields.
2. Instance Ownership Transfer, sign-in and identity-provider authority changes, Platform privilege elevation or delegation, administrative Platform MFA reset, and critical credential replacement require a fresh user-verifying security key or passkey at final apply. An owning domain may add another action only with a documented security consequence and versioned catalog change; ordinary reads and low-risk saves remain baseline.
3. The Instance Owner must always retain at least one verified WebAuthn method. Initial Owner bootstrap, same-owner recovery, and replacement-owner recovery verify the method before ownership-bound access becomes available, and ownership transfer requires the target to be phishing-resistant ready before nomination can become acceptable.
4. A Platform Role derives phishing-resistant readiness when any contained Platform Permission reaches an action in the stronger class. Assigning that role to an existing Operator fails before apply unless the target has a verified WebAuthn method; a new invitation may carry the role, but acceptance cannot atomically activate it until the intended identity verifies such a method.
5. A Custom Platform Role revision that introduces a stronger requirement includes affected Operators and pending invitations lacking readiness in its revision-bound impact preview. Apply remains blocked until every continuing assignment is ready or the actor explicitly changes the assignment set through its own authorized workflow; the server never partially updates role authority or silently drops permissions.
6. TOTP remains valid for baseline Platform sign-in and baseline Step-up actions. It cannot satisfy, downgrade, or create a proof for a phishing-resistant action even when no WebAuthn method is currently usable; the operator enrolls or recovers a compliant method before continuing.
7. A phishing-resistant proof records the verified assurance class and credential identity as safe evidence and remains bound to section 4.8's actor, Session, action, target/scope, revisions, freshness, and idempotency constraints. A proof from another method, action, Session, or earlier policy revision cannot be promoted or replayed.
8. Losing or removing the last usable WebAuthn method while Owner or role requirements remain moves the actor into the applicable recovery or readiness-blocked path and denies affected high-risk applies. It never makes TOTP equivalent, removes the role automatically, or grants an assurance grace period.
9. The Platform Console presents the exact blocked action and next step in plain language, offers enrollment or recovery where authorized, and keeps protocol and assurance codes in diagnostic detail. It never hides the action as if permission were absent or shows a confirmation that cannot satisfy the server requirement.
10. Audit and security evidence record the action's required assurance, verified method class, credential identity, policy/catalog revision, result, and safe failure category without storing challenges, private material, biometric data, TOTP codes, or authenticator payloads.

### 4.13 Identity-provider authentication does not replace Platform MFA

1. A configured external identity provider may authenticate the human identity and satisfy deployment sign-in policy, but it does not issue or satisfy a Platform MFA Method, Platform Session, Step-up Platform Verification, Phishing-resistant Platform Verification, Platform Role, or Platform Permission.
2. Provider sessions, remembered-device state, upstream MFA prompts, and `amr`, `acr`, assurance-level, authentication-context, or equivalent claims are identity-authentication evidence only. The Platform API never maps them to local MFA readiness or action verification, even when their names resemble supported Platform methods.
3. After successful identity-provider authentication, every Instance Owner and Platform Operator completes a challenge with an Arclayer-enrolled Platform MFA Method before a Platform Session is issued. A critical action still requires an Arclayer-verified security key or passkey bound to the local action context under section 4.12.
4. Invitation acceptance, Operator MFA Recovery, Owner bootstrap or recovery, and Platform Session re-entry cannot import, enroll, or synthesize a local method from provider claims. The actor completes the applicable bounded local enrollment or challenge flow.
5. When enterprise sign-in and Platform MFA occur consecutively, the UI states that identity confirmation succeeded and Platform security verification remains. It does not present the second challenge as a provider failure, repeat the provider's protocol terminology, or claim that one prompt upgraded the other.
6. Identity-provider configuration has no “trust provider MFA,” claim-mapping, assurance-bypass, or remembered-device compatibility setting. Introducing federated Platform MFA assurance would require a new explicit security decision, migration contract, provider validation model, and direct downgrade tests.
7. Audit and diagnostics may record the provider identity and safe upstream authentication result separately from the local Platform method and verification result. They never merge the two evidence classes or store provider tokens, raw claims, local factors, challenges, or authentication payloads.

## 5. Product copy and i18n

## 6. Non-goals

- A generic Access or OAuth settings page.
- A second User directory or Workspace member-management surface.
- Immediate Platform authority at invitation-send time or before mandatory MFA enrollment completes.
- Using Platform Operator Invitation to transfer Instance Owner authority.
- Restricting all invitations to the Instance Owner or treating one team-management permission as unlimited role delegation.
- Silently removing disallowed permissions or replacing changed roles while an invitation is accepted.
- Direct per-operator permission grants, denies, or exceptions.
- Editing or deleting Built-in Platform Roles, or representing the Instance Owner as an all-access role.
- Delaying Custom Platform Role permission removal until logout, copying permissions into a Platform Session, or rolling out one role revision to assignments gradually.
- Silently moving a pending invitation to a newer role revision.
- Automatically cancelling every Accepted Platform Operation on authority loss or allowing captured acceptance evidence to authorize new actions.
- Reporting irreversible or partially committed work as cancelled merely because its original actor lost permission.
- Hard-deleting an operator during routine offboarding, retaining resumable role authority, or restoring access without a new invitation.
- Treating Platform offboarding as Product account disablement, Workspace removal, or an Instance Owner transition.
- Immediate or one-sided ownership reassignment, a dual-owner grace period, or any transient ownerless state.
- Allowing the new owner to remain a role-authorized Platform Operator or letting the former owner retain implicit full authority.
- Allowing Platform Operators to vote, self-promote, or use Platform RBAC as Ownership Recovery.
- Giving a recovery custodian or support actor ordinary Console/API access, silently bypassing the declared hold policy, or storing raw recovery proof in general Audit.
- Treating Platform login MFA as permanently fresh for every high-risk action or challenging MFA for every routine mutation.
- Letting the frontend infer step-up requirements or allowing a verification proof to grant permission, change scope, survive relevant revision drift, or authorize a second operation.
- Sharing one Platform Session across devices, importing a Product Session, refreshing past absolute expiry, silently replacing an expired Session, or using an arbitrary Session-count cap as the lifecycle policy.
- Treating a recovery code or administrative MFA reset as a Platform Session, temporary authority, role change, administrator impersonation, Owner recovery path, or bypass around identity verification and new MFA enrollment.
- Retaining target Platform Sessions, Step-up proofs, old factors, or unused recovery codes after MFA recovery begins, or allowing the Instance Owner to use ordinary Operator MFA reset.
- Using email, SMS, voice, recovery codes, Product sign-in state, or an unverified enrollment as a routine Platform MFA Method or Step-up proof.
- Requiring only WebAuthn or only TOTP in the initial product, exposing secrets or protocol fields in primary UI, or allowing removal of the last verified Platform MFA Method.
- Allowing TOTP, recovery codes, prior login MFA, frontend confirmation, or any delivery channel to satisfy or downgrade a phishing-resistant action requirement.
- Assigning or activating a role with phishing-resistant actions for an Operator without a verified security key/passkey, or allowing an Owner or affected Operator to remove their last such method.
- Maintaining separate hard-coded high-risk action lists in roles, pages, or invitation flows instead of consuming the trusted action and permission catalog.
- Treating identity-provider MFA, assurance claims, remembered-device state, Product MFA, or an SSO Session as a Platform MFA Method, Platform Session, or action-bound verification proof.
- Adding a provider-MFA trust toggle or silently skipping local Platform verification because an upstream prompt occurred.
- One all-powerful `platform.manage` permission or a UI-only authorization check.
- Summary cards that restate visible counts without identifying a security problem or action.
- Raw protocol, Provider, permission, or state-machine terminology as primary product copy.

## 7. Migration contract

The hard cut moves retained registration, provisioning, and identity-provider capabilities out of `/system/settings/access` and `/system/settings/oauth` into their owning Identity & Access surfaces. The old routes, registry entries, search items, page wrappers, and duplicated translation keys are removed once every retained capability has an exact route, Platform Permission, readiness state, and audit contract. Missing Platform team, role, MFA, or Session capabilities fail visibly until implemented; no legacy settings page or super-admin flag acts as a compatibility facade.

The Product Application account-menu entry and Platform Console return link change atomically to configured typed cross-host targets. No redirect bridge, one-time Product token, Workspace-bearing query parameter, shared cookie, or Product-to-Platform permission projection survives the cutover. Any legacy super-administrator assignment is migrated through the explicit exactly-one Instance Owner rule; no other existing User, Workspace administrator, or unaccepted invite is silently promoted to an active Platform Operator. Existing broad administrator or team-management flags receive no automatic invitation permission, Delegable Platform Authority, direct per-operator permission, or synthetic all-access role during migration. Legacy sessions and permission caches are not imported as role authority; the cutover establishes server-authoritative role revisions before issuing Platform Sessions. Existing in-flight Platform work must either be migrated with complete accepted-operation authorization and idempotency evidence or reach an explicit terminal state before cutover; anonymous or unevidenced work is never grandfathered as authorized. Legacy disabled or removed platform actors migrate as Deactivated Platform Operators with ended assignments and retained evidence, never as deleted identities, resumable roles, or active eligibility. Any existing owner-change path is retired in favor of the two-party transfer contract; migration never manufactures a second owner or maps a role assignment to ownership. The Platform Host cannot become the production operator entry until its managed or self-hosted Ownership Recovery path is configured, recovery material is delivered to the declared custody boundary, and a non-production recovery rehearsal proves exactly-one-owner and Session-revocation behavior. Legacy session issue time, Product MFA, confirmation dialogs, and frontend route guards are not migrated as step-up proof; every classified action uses the new server-validated action-bound contract.

Legacy Product or shared administrator Sessions are not imported into the device-scoped Platform Session inventory. The cutover issues independently revocable Platform Sessions under the current versioned inactivity and absolute-lifetime policy only after the required Platform MFA challenge.

Legacy Product two-factor recovery codes, password-reset links, support reset flags, shared administrator credentials, and existing factor-recovery sessions are not accepted as Platform MFA Recovery proof. Every migrated non-owner operator completes current Platform MFA enrollment to receive a new one-time recovery-code set; the Instance Owner's recovery readiness is established through the separate Ownership Recovery contract.

Legacy Product passkeys, TOTP secrets, email/SMS verification state, and remembered-device flags are not silently imported as Platform MFA Methods. Every migrated Instance Owner and Platform Operator verifies at least one supported Platform method under the configured Platform origin before receiving Platform authority; no unsupported method is grandfathered through a compatibility facade.

Before cutover, the Instance Owner verifies a security key or passkey, and every Operator assigned a role containing phishing-resistant actions either verifies one or has that role removed through an explicit reviewed authority change. Migration does not reinterpret TOTP or legacy Product MFA as phishing-resistant readiness, activate a partially usable privileged role, or preserve a weaker verification fallback for critical actions.

Legacy SSO sessions, remembered-device state, MFA flags, `amr`/`acr` mappings, and provider assurance configuration are not migrated as Platform MFA readiness or verification proof. Every identity-provider-authenticated Owner and Operator completes the local Platform enrollment and challenge contracts before cutover; no provider-specific compatibility switch bypasses them.

## 8. Acceptance contract

- Eligibility projection tests prove only identities currently recorded as the Instance Owner or an active Platform Operator receive `eligible`, while pending, revoked, disabled, stale, and ordinary Workspace-authorized identities do not.
- Invitation lifecycle tests prove send does not grant authority, only the intended identity may accept, MFA enrollment precedes activation, and operator status plus intended role assignments commit atomically.
- Delegation tests cover Instance Owner invitation, explicitly authorized operator invitation, direct-API denial without invitation permission, combined-role escalation, non-delegable authority, and roles outside the inviter's Delegable Platform Authority.
- Role-model tests cover immutable Built-in Platform Roles, independent copy-to-custom behavior, Custom Platform Role creation, multi-role additive union and deduplication, exact endpoint checks, and absence of per-operator grants or denies.
- Role-change tests cover server preview, permission and affected-operator diffs, self-impact, expected-revision conflict, changed assignments/catalog, Delegable Platform Authority, atomic all-assignment adoption, and complete Audit evidence.
- Session authorization tests prove existing sessions remain authenticated while the next request observes added or removed permissions from the latest role revision, including concurrent requests and stale cache/projection attempts.
- Invitation tests prove a replaced role revision invalidates every bound pending invitation explicitly and never substitutes the new revision.
- Accepted-operation tests revoke authority before acceptance, after acceptance, between background phases, before retry/confirmation, and during partial external effects; only the originally accepted scope continues, while every new command uses current authority.
- Cancellation tests prove only an owning-domain safe boundary and currently authorized cancellation command can stop remaining work, committed effects stay explicit, idempotent repeats do not invent a second result, and Audit attributes acceptance and cancellation separately.
- Offboarding tests cover preview, expected-revision conflict, revocation barrier, eligibility removal, all-Session revocation, assignment end-dating, inbound/outbound pending-invitation invalidation, accepted-operation continuity, Product/Workspace authority isolation, and retained Audit attribution.
- Re-entry tests prove no pause/restore path exists and a Deactivated Platform Operator must complete a new invitation, current role validation, MFA requirement, activation, and Platform Session issuance.
- Instance Owner tests deny ordinary operator removal and require the separate ownership-transfer contract.
- Ownership-transfer tests cover eligible and ineligible targets, pending nomination with no authority change, fresh target MFA, explicit acceptance, revision drift, exactly-one-owner concurrency, target-role end-dating, former-owner selected-role or deactivation outcomes, both-principal Session revocation, Product Session isolation, invitation revalidation, and Accepted Platform Operation attribution.
- Failure-injection tests at every transfer boundary prove neither dual ownership nor an ownerless deployment is observable and no failed acceptance reports success.
- Ownership-recovery tests cover same-owner MFA restoration, unavailable-owner replacement, self-hosted and managed proof adapters, notification/hold policy, proof replay, target identity and MFA failure, current-owner revision drift, exactly-one-owner concurrency, former-owner deactivation, Session revocation, invitation revalidation, accepted-operation continuity, and recovery-material rotation.
- Adversarial tests prove Platform Roles, Operator quorum, Product Sessions, support identity, recovery-custodian identity, leaked UI state, and ordinary Platform APIs cannot initiate or complete recovery authority.
- Recovery rehearsals verify the out-of-Console surface remains usable during Console failure and that diagnostics and Audit omit raw proofs and identity documents.
- Step-up tests cover classified and unclassified actions, exact actor/Session/action/target/scope/revision/idempotency binding, current permission recheck, freshness expiry, role/session/policy/preview drift, same-idempotency network retry, cross-action replay denial, and accepted-operation evidence.
- Browser tests cover successful and failed MFA, keyboard-only flow, preserved review context, plain-language action/scope copy, both locales, expired verification, permission loss during challenge, and absence of raw factor/proof terminology.
- Platform Session tests cover independent browsers and devices, inactivity and absolute expiry, activity bounded by the absolute deadline, refresh and rotation at that deadline, new MFA-backed sign-in, individual/current/all-other revocation, concurrent revocation and request races, safe inventory fields, policy revision, Step-up invalidation, Product Session isolation, and absence of an implicit Session-count cap.
- Platform Session browser tests cover current-device identification, created/recent-activity/expiry presentation, single-device and all-other-device confirmation, server-confirmed revocation results, expired-session recovery, keyboard operation, and stable plain-language copy in both locales without raw token, fingerprint, or state-machine terminology.
- MFA-recovery tests cover one-time code issuance and non-disclosure, hashed storage, regeneration invalidation, identity authentication before use, single-use and concurrent replay, all-Session/factor/code/Step-up revocation, no authority during setup, new enrollment and Session issuance, retained current roles, Deactivated Operator denial, and Accepted Platform Operation continuity.
- Administrative-reset tests cover exact reset permission, different active non-owner target, action-bound step-up, impact preview and revision drift, idempotency, concurrent offboarding, no factor visibility or selection, Product authority isolation, Owner exclusion, and complete safe Audit evidence.
- MFA-recovery browser tests cover save-once recovery-code presentation, regeneration consequences, used/invalid/expired code errors, setup-required state, administrative reset confirmation, keyboard-only enrollment, failure recovery, and stable natural copy in both locales without temporary-access or impersonation language.
