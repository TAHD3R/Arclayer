# Backend i18n Contracts

This code-spec defines executable backend localization contracts for request locale resolution, translation lookup, and error message localization.

## Scenario: Request Locale Resolution and Translation Runtime

### 1. Scope / Trigger

- Trigger: adding or changing backend APIs, middleware, exception handlers, locale resources, or plugin/runtime locale behavior.
- Applies to:
  - `apps/api/src/core/i18n.py`
  - `apps/api/src/core/middleware/locale.py`
  - API error localization in exception handlers.

### 2. Signatures

- Defaults and supported locales:
  - `DEFAULT_LOCALE = "zh-CN"`
  - `SUPPORTED_LOCALES = ("zh-CN", "en-US")`
- Request locale resolution:
  - `get_request_locale(request: Request | None, *, default_locale: str | None = None) -> str`
- Runtime locale context:
  - `get_current_locale() -> str`
  - `set_current_locale(value: str) -> Token`
  - `reset_current_locale(token: Token) -> None`
- Translation helpers:
  - `t(namespace_or_key, key_or_options=None, *, locale=None, default=None, **kwargs) -> str`
  - `translate(namespace: str, key: str, *, locale: str) -> str | None`
  - `translate_error(error: str, *, locale: str) -> str | None`
  - `localize_message(message: str, *, error: str | None, locale: str) -> str`
- Locale resource path management:
  - `register_locale_path(path: Path) -> None`
  - `clear_locale_cache() -> None`

### 3. Contracts

- Backend request locale resolution must follow this runtime order:
  - `X-Locale` header
  - `lang` query parameter
  - default locale passed from middleware (`workspace` or `system` scope)
  - `Accept-Language` only when no explicit locale and no default locale is available
  - hard fallback `zh-CN`
- `LocaleMiddleware` must set request-local locale context before downstream handlers and reset the context in `finally`.
- Locale normalization must map:
  - any `zh*` input to `zh-CN`
  - any `en*` input to `en-US`
  - unknown locales to `DEFAULT_LOCALE`
- Exception handlers must localize message text via `localize_message(message, error=..., locale=...)` and keep `error` code stable.
- Error localization keys must live in `errors` namespace and be addressed by stable error code.
- `register_locale_path` is append-only for existing directories and must clear `_load_locale` cache after path registration.
- `translate` must try requested locale first and then fallback to `DEFAULT_LOCALE` when locale is not default.
- Backend i18n formatting uses Python `str.format_map` semantics (`{name}` placeholders), not frontend i18next interpolation (`{{name}}`).

### 4. Validation & Error Matrix

| Condition | Required behavior |
|---|---|
| `X-Locale: en-US` provided | Resolve locale to `en-US` regardless of query/default |
| `lang=zh_CN` query provided | Normalize to `zh-CN` |
| No explicit locale and workspace default exists | Use workspace default from middleware |
| No explicit locale and no workspace/system default | Parse `Accept-Language` first language token |
| Namespace/key missing in requested locale | Fallback lookup in `zh-CN` |
| Namespace/key missing in both locales | Return `None` from `translate`; `t()` falls back to default or key |
| `localize_message` called with `error=None` | Return original message text unchanged |
| Invalid locale JSON file | Ignore bad file payload, continue loading other resources |

### 5. Good/Base/Bad Cases

- Good: API handler raises `Forbidden(..., error="API_KEY_INVALID")` and exception handler localizes message using `errors.API_KEY_INVALID`.
- Good: middleware resolves workspace-scoped default locale through `read_core_default_locale(...)` and applies it request-wide.
- Base: locale resource key exists only in `zh-CN`; `translate(..., locale="en-US")` falls back to `zh-CN`.
- Bad: directly returning hardcoded Chinese or English error strings from service logic while omitting a stable error code.
- Bad: adding backend interpolation keys using `{{name}}` placeholders that only frontend i18next understands.

### 6. Tests Required

- API tests for localized errors must assert stable `error` codes and locale-dependent `message`.
- Locale middleware tests must cover priority order:
  - header
  - query
  - workspace/system default
  - `Accept-Language`
  - fallback locale
- Translation runtime tests must verify:
  - locale normalization
  - fallback to `zh-CN`
  - cache reset behavior after `register_locale_path` / `clear_locale_cache`.
- Any new public error code must include `zh-CN` and `en-US` mapping in locale resources.

### 7. Wrong vs Correct

#### Wrong

```python
raise Forbidden("API key invalid for this workspace")
```

#### Correct

```python
raise Forbidden("API key invalid", error="API_KEY_INVALID")
```

The exception handler localizes `message` by `error` code and keeps the public `error` contract stable.
