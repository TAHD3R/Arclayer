3. 关键差距分析 (Gap Analysis)

以下列出从当前状态到可交付 AI 功能所需弥补的关键差距，按优先级排列：

[P0] LLM Provider 抽象层

缺失

这是所有 AI 功能的基础依赖。需建立统一的 LLM Provider 接口， 支持至少 OpenAI 和 Anthropic，后续可扩展。需处理 API key 管理、速率限制、错误重试、流式响应。

[P0] AI Settings & 配置模型

缺失

需要在 config.py 中新增 AISettings，包含 provider 选择、 API key、默认 model、速率限制、token 上限等配置项。对应环境变量前缀 AI__。

[P1] Embedding Service

缺失

向量化文本/图片内容，存入 pgvector。这是语义搜索、RAG、内容相似度分析的基础。 pgvector 基础设施已就绪，可直接使用。

[P1] Prompt Registry

缺失

集中管理 prompt 模板，支持版本控制、变量插值、A/B 测试。需要考虑多租户下的 prompt 隔离或共享。

[P1] AI 数据库模型 & 迁移

缺失

需要创建：embedding 向量表、prompt 模板表、AI 请求日志/审计表、Agent 会话表、 使用量/计费表。考虑多租户 schema 隔离策略。

[P2] AI API 模块

缺失

创建 src/modules/ai/，提供 REST API 端点：chat/completion、embedding、 content/generate、content/analyze 等。遵循现有 router → service → repository → schema 模式。

[P2] Agent 运行时

缺失

实现 Agent 循环（ReAct/Plan-Execute），工具注册与调用，多步推理。可参考 .agents/ 中 MCP 协议的技能定义模式。

[P2] 前端 @platejs/ai 集成

缺失

激活 Plate.js AI 插件，实现编辑器内 AI 辅助写作（续写、改写、翻译、摘要等）。 依赖后端 AI API 模块先就绪。

[P3] AI 事件驱动工作流

缺失

订阅事件总线，自动化 AI 处理：content.created → 自动摘要/标签， asset.uploaded → 图片分析/alt text，content.published → SEO 优化建议。

[P3] AI 使用量计费 & 审计

缺失

Token 使用量追踪、按租户/项目计费、速率限制、AI 请求审计日志。 对 SaaS 多租户场景尤其重要。

4. 推荐实现路线图

Phase 0 — 基础设施验证 ✅ 已完成

pgvector 部署、Meilisearch 部署、插件系统、事件总线、后台任务队列、多租户隔离 — 均已就绪，为 AI 功能提供坚实基础。

Phase 1 — AI 核心基础设施 (预计 2-3 周)

目标: 建立最小可行的 AI 调用链路。可以从前端调用后端，后端调用 LLM，返回结果。

  • [P0] LLM Provider 抽象层 — 支持 OpenAI + Anthropic，含流式响应
  • [P0] AISettings 配置模型 — 环境变量、Settings 类
  • [P1] AI 数据库迁移 — embedding 表、prompt 表、audit_log 表
  • [P2] AI API 模块 — 基础 /ai/chat 端点
  • [P2] 前端 AI Tab 激活 — 将占位 UI 替换为真实的 AI 内容类型生成
  • 集成测试验证全链路

Phase 2 — AI 功能深化 (预计 3-4 周)

目标: 提供有实际价值的 AI 辅助内容管理功能。

  • [P1] Embedding Service — 文本/图片向量化 + pgvector 存储
  • [P1] Prompt Registry — 模板管理与版本控制
  • [P2] @platejs/ai 集成 — 编辑器内 AI 辅助写作
  • [P3] AI 事件驱动工作流 — 自动摘要/标签/alt text
  • 语义搜索 POC

Phase 3 — Agent 系统 (预计 4-6 周)

目标: 实现产品内 AI Agent，支持多步推理和工具调用。

  • [P2] Agent 运行时 — ReAct 循环，工具注册与调用
  • 内容管理 Agent — 自动内容审核、分类、关联推荐
  • 数据分析 Agent — 内容表现分析、用户行为洞察
  • [P3] AI 使用量计费 & 审计
  • Agent 工作流可视化 UI

Phase 4 — 高级 AI 能力 (预计 6-8 周)

目标: RAG、多模态、自定义模型支持。

  • RAG 内容问答 — 基于项目内容的智能问答
  • 多模态 AI — 图片生成、视频分析
  • 自定义模型支持 — 允许用户配置自己的 LLM endpoint
  • AI 工作流编排器 — 可视化 DAG 工作流设计器

5. 待决策的架构问题

#决策点选项影响
1 LLM Provider 方案 A) 自建抽象层
B) 使用 Vercel AI SDK
C) 使用 LangChain 		A: 最大灵活性，更多开发工作
B: JS 生态，需要 Node 侧代理或改用 JS 后端
C: Python 生态成熟，但引入重依赖
2 Agent 框架 A) 自建轻量 Agent 循环
B) LangGraph
C) CrewAI 		A: 完全控制，需自行实现工具调用
B: 成熟的图状态机，学习曲线陡
C: 多 Agent 协作，较轻量
3 AI 功能部署模型 A) 插件 (arclayer-ai)
B) 内置模块 (src/modules/ai/)
C) 独立微服务 		A: 可选安装，松耦合
B: 紧密集成，开发更快
C: 独立扩缩容，运维复杂
4 多租户 AI 隔离策略 A) 共享 LLM 调用，按 token 计费
B) 每租户独立 API key
C) 混合模式 		影响计费模型、数据隐私、速率限制策略
5 向量存储方案 A) pgvector (已部署)
B) 独立向量数据库 (Pinecone/Qdrant/Milvus) 		A: 零额外运维，PostgreSQL 生态
B: 更高性能，更丰富检索能力
建议: 对于 Phase 1，推荐方案 A-A-A-A-A（自建抽象层 + 自建 Agent + 内置模块 + 共享计费 + pgvector）。 这是最快的启动路径，后续可根据实际需求迁移到更专业的方案。
