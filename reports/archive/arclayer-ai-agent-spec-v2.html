1. Extensions 系统 v2

1.1 概述与边界

设计目标构建 CMS 级别、多租户感知、支持安装/激活/配置/卸载的 Extensions 系统。参照 Strapi/Directus 模式，在 pluggy 类型化 Hook 骨架之上补齐消费端、元信息清单、数据库激活、Admin UI 扩展（构建时打包）、依赖管理、分发机制。
v2 关键架构原则Extension 状态必须在三个独立域中管理，不能混入单一状态机：Package Install（文件系统/包管理）→ Process Runtime（进程加载/卸载）→ Workspace Activation（每租户启用/配置）。所有 Registry Consumer 必须在请求时进行 tenant-aware 解析，不能在启动时进行 Workspace 范围的全局注册。

1.2 Extension Manifest

每个 Extension 根目录放置 extension.json 声明式元信息。无须加载代码即可读取。Schema 定义与 v1.0 基本一致，v2 增加了 trust_level 字段。

{
  "$schema": "https://arclayer.dev/schemas/extension-v2.json",
  "name": "arclayer-ai-agent",
  "version": "1.0.0",
  "trust_level": "trusted",          // "trusted" | "untrusted" — v2 新增
  "entry": "src/plugin.py",
  "requires": {
    "platform": ">=1.0.0",
    "python": ">=3.12",
    "extensions": { "arclayer-core": ">=1.0.0" }
  },
  "provides": {
    "services": ["ai-service"],
    "agents": ["content-writer", "content-analyzer"],
    "adminSlots": [
      {"name": "ai-sidebar", "location": "sidebar", "bundle": "dist/admin.js"}
    ],
    "middlewares": ["ai-rate-limiter"],
    "providers": [
      {"type": "ai", "name": "openai"},
      {"type": "ai", "name": "anthropic"}
    ]
  },
  "permissions": ["content:read", "content:write", "asset:read", "workspace:settings"],
  "config_schema": { "type": "object", "properties": { ... } },
  "distribution": { "type": "npm", "package": "@arclayer/extension-ai-agent" }
}

1.3 三状态机模型 v2 关键变更

v1.0 问题：将 ABSENT/INSTALLED/ACTIVATED/REGISTERED/BOOTSTRAPPED/READY/DESTROYED 放入单一线性状态机。INSTALLED 是平台状态，ACTIVATED 是 Workspace 状态，REGISTERED 是进程状态——它们发生在不同时间、由不同角色触发、有不同的生命周期。

状态机 A: Package Lifecycle（平台管理员触发）

ABSENT ──install()──▶ INSTALLED ──upgrade()──▶ UPGRADING ──▶ INSTALLED
  │                      │
  └──                    └── uninstall() ──▶ UNINSTALLED ──▶ ABSENT

触发者: 平台管理员 / CI Pipeline
存储:   extensions 表 (source_type, source_url, manifest)
影响:   文件系统 (npm install / git clone / 本地路径)

状态机 B: Process Runtime Lifecycle（应用启动/关闭触发）

UNLOADED ──load()──▶ LOADED ──register()──▶ REGISTERED ──bootstrap()──▶ READY
                         │                                                    │
                         └── unload() ────────────────────────── DESTROYED ◀──┘

触发者: 应用启动 / 关闭
存储:   进程内存 (ExtensionManager.runtime_state)
关键:   加载失败 Extension 标记为 error，不影响其他 Extension
       运行时状态与 Workspace 激活状态独立

状态机 C: Workspace Activation Lifecycle（Workspace 管理员触发）

INACTIVE ──activate()──▶ ACTIVE ──deactivate()──▶ INACTIVE
                           │
                           └── config_update() ──▶ ACTIVE (config changed)

触发者: Workspace 管理员 / API
存储:   workspace_extensions 表 (enabled, config)
时点:   Per-request 解析，非启动时全局注册
影响:   该 Workspace 的请求可见 Extension 注册的资源

三状态机协调规则

1. Extension 必须先 Package INSTALLED 才能 Process LOAD
2. Process 可以 LOAD 一个 Workspace 中尚未激活的 Extension（代码就绪）
3. 请求到达时，同时检查 Process READY + Workspace ACTIVE 才使用 Extension 资源
4. Workspace deactivate 不需要 Process unload
5. Package uninstall 必须先确保所有 Workspace deactivate + Process unload

1.4 Tenant-Aware Registry Contract v2 关键变更

v1.0 问题：Registry Consumer 绑定表只标注了"谁消费"，但未标注消费时点（启动时 vs 请求时）和租户上下文。启动时进行 Workspace 范围的全局注册在共享多租户进程中不成立。

Registry Consumer 合约

RegistryConsumer消费时点Tenant-Aware 要求
ServiceRegistry FastAPI Depends() Request-Time resolve(name, workspace_id, user_id) — 每次请求传入租户上下文，返回 scoped 实例
MiddlewareRegistry AppFactory Startup-Time 中间件在启动时全局注入，但内部逻辑检查 request.state.workspace_id 做租户感知
ContentTypeRegistry Content Model Builder Request-Time list_types(workspace_id, activation_revision) — 缓存 key 包含 workspace_id + revision
ProviderRegistry Storage/Search/Email 工厂 Request-Time resolve_provider(type, workspace_id) — Provider 配置 per-Workspace
CustomFieldRegistry field_type_registry Request-Time 缓存 key 包含 workspace_id + extension version + activation revision
AdminSlotRegistry Admin UI API → Build Pipeline Build-Time + Request-Time 构建时收集所有 Extension 的 slot 声明。运行时 API 按 workspace activation 过滤
PolicyRegistry Permission Guard Request-Time evaluate(policy_name, workspace_id, user_id, resource, action)

Activation Revision 机制

-- workspace_extensions 表追加 revision 字段
ALTER TABLE workspace_extensions ADD COLUMN revision BIGINT DEFAULT 1;

-- 每次 activate/deactivate/config_update 递增 revision
-- Consumer 缓存 key 格式: registry:{name}:ws:{workspace_id}:rev:{revision}
-- ExtensionManager 发布 invalidation event: extension.config_changed.{workspace_id}

1.5 数据库驱动激活

与 v1.0 设计一致，但明确区分了三个时点：

应用启动 (一次性)
  ├─→ 扫描已安装 Extension → extensions 表
  ├─→ 加载所有 INSTALLED Extension 到进程 (Process Runtime → READY)
  └─→ 不查询 workspace_extensions（那是请求时的事）

请求到达 (每次)
  ├─→ 从 Token 解析 workspace_id
  ├─→ 查询 workspace_extensions WHERE workspace_id=? AND enabled=true
  ├─→ 获取该 Workspace 的 activation_revision
  ├─→ Registry Consumer 使用 tenant-aware API 解析资源
  └─→ 缓存结果 (key 包含 workspace_id + revision)

1.6 Extension 信任模型 v2 关键变更

v1.0 问题：使用"安全沙箱"描述进程内 Python 代码的权限声明，这是不诚实的。Python 代码加载进同一进程可以访问环境变量、文件系统、网络、内存、内部服务、全局注册表。Permission 声明和审计日志不能"沙箱化"不受信任的 Python 代码。

双级信任模型

信任级别适用对象隔离机制安全保证Phase
受信任 (Trusted) 第一方 + 认证第三方 Permission 声明 + 审计日志 + API 调用审计 防止意外越权，不防恶意代码。依赖代码审查和签名验证。 Phase 2
不受信任 (Untrusted) Marketplace / Community 进程隔离 (subprocess/container/WASM) + RPC boundary + deny-by-default egress 真正隔离。Extension 无法访问主进程内存、文件系统、网络。 独立项目（不在当前路线图）

受信任 Extension 的安全措施 (Phase 2)

措施实现
Manifest Permission 声明Extension 声明所需权限（content:read 等）。加载时校验。
API Client FacadeExtension 必须使用框架提供的 ExtensionContext 访问资源，不能直接 import ORM/httpx。
数据库访问封装Extension 通过 tenant-scoped Repository 访问数据，工作空间隔离自动执行。
网络出站限制Extension 使用框架提供的 HttpClient（deny-by-default egress，需要 manifest 声明域名白名单）。
审计日志所有 Extension API 调用记录到 extension_audit_log。
错误隔离单个 Extension 异常不影响其他 Extension 和应用主体。
包签名验证Extension 包需有数字签名，安装时验证。

1.7 Admin UI 扩展插槽 v2 变更

v1.0 问题：返回 slot 元数据的 API 不足以渲染 React 组件。必须选定组件加载模型。运行时动态加载任意 React 组件是安全风险和运维问题。

选定的加载模型：构建时打包 (Build-Time Bundling)

工作流程:
  1. Extension 在 extension.json 中声明 adminSlot + bundle 路径
     {"name": "ai-sidebar", "location": "sidebar", "bundle": "dist/admin.js"}

  2. 构建时，CI/CD 扫描所有已安装 Extension 的 adminSlot 声明
     收集 extension admin bundles → 打包进 apps/admin 构建产物

  3. 运行时，前端根据 GET /api/v1/admin/slots?location=sidebar
     返回的 slot 列表按 priority 渲染（组件已在 bundle 中）
     API 已按 workspace activation + user permission 过滤

  4. Slot 组件接收受限的 ExtensionContext（不包含 broad token）
     只能通过 SDK 提供的 hooks 与后端交互

优点:
  - 组件在构建时已知，可做 tree-shaking 和静态分析
  - 无运行时动态加载的安全风险
  - 签名验证在构建时完成

限制:
  - 安装/更新 Extension 需要重新构建 Admin（适合 CI/CD 流程）
  - Phase 2 只支持此模型

未来可选: Module Federation (Webpack/Vite) 或 iframe 隔离
          作为 Phase 4+ 的可选方案

2. AI 基础设施 v2

2.1 src/llm/ 模块结构

与 v1.0 一致。v2 追加 LLMRuntime 作为高层入口，集中管理 Key 解析、审计、预算检查、模型策略强制：

class LLMRuntime:

    def __init__(self, client: LiteLLMClient, key_resolver: VirtualKeyResolver,
                 audit: AuditService, policy: ModelPolicyEngine): ...

    async def chat(self, messages, context: LLMRequestContext) -> ChatResult:

        # 3. 预算预检查 (预估 token → 冻结预算)

2.2 LiteLLM Proxy 集成

与 v1.0 一致。v2 追加：

  • Master Key 仅用于 Key 管理操作（create/delete/update virtual key）。常规推理请求使用 Virtual Key 本身作为 Bearer auth。
  • LiteLLM 需作为关键基础设施对待：独立数据库、健康检查、故障模式测试、本地 mock。
  • 重试策略 + 熔断器 + Provider 回退在 LiteLLM 配置层处理。

2.3 AISettings 配置

与 v1.0 一致，追加 AI__OBSERVABILITY_LOG_LEVEL 和 AI__BUDGET_PREFLIGHT_ENABLED。

2.4 多租户 Key 模型 v2 关键变更

v1.0 问题：Virtual Key 优先级 User → Workspace → Platform 存在风险。如果用户属于多个 Workspace，用户级 Key 可能在未授权的 Workspace 中被使用，导致跨租户计费泄露。

v2 Workspace-First Key 模型

Key 解析规则（v2 修正）:
  请求必须携带 workspace_id。

  1. Workspace 拥有独立 Key → 使用 workspace/{id}
     这是最优先的策略。Workspace 管理员完全控制 AI 支出。

  2. Workspace 未配置 Key，但用户在该 Workspace 中显式授权了个人 Key
     → 使用 user/{user_id}:workspace/{workspace_id}
     用户 Key 必须显式链接到具体 Workspace 才能使用。
     防止用户在 Workspace B 中意外消耗在 Workspace A 中配置的 Key。

  3. 以上均不满足，Workspace 策略允许使用平台共享 Key
     → 使用 platform/shared
     平台管理员控制哪些 Workspace 可以使用共享 Key。

  LiteLLM Virtual Key 注册:
  注册用户 Key 到 LiteLLM 时需要加密传输实际 credential。
  ai_api_keys 表存储 key_hash（SHA-256，用于展示/去重），
  实际 credential 经 KMS/信封加密后存储，或直接注册到 LiteLLM 后丢弃本地副本。

Key 生命周期

操作:
  - 创建: POST /api/v1/workspaces/{id}/ai-keys  (Workspace Key)
          POST /api/v1/users/me/ai-keys           (User Key)
  - 链接: POST /api/v1/users/me/ai-keys/{id}/grant/{workspace_id}
  - 轮换: POST /api/v1/ai-keys/{id}/rotate
  - 撤销: DELETE /api/v1/ai-keys/{id}
  - 同步: 定时任务将本地 Key 状态与 LiteLLM Virtual Key 对账
  - 过期: 检测未使用的 Key → 通知 → 自动撤销

3. Agent 系统 v2

3.1 概述

与 v1.0 定位一致。v2 关键变更：

  • PydanticAI 是执行引擎（非装饰）。AgentRunEngine 委托给 pydantic_ai.Agent.run()，不手工处理 tool calls。PydanticAI 负责 tool call 循环、结构化输出校验、重试。
  • 只读 Agent 先于可写 Agent。Phase 3A 所有 Agent 仅读权限。Phase 3B 引入写操作 + 审批门 + Dry-Run。
  • Prompt Injection 防护：工具执行时必须将用户内容与系统指令分离。每个 tool call 在 execution time 重新校验权限。
  • Correlation ID 贯穿全链路：HTTP Request → Agent Session → LiteLLM Request → Tool Call → Extension Audit → Background Task。

3.2 Agent 运行时

与 v1.0 设计一致，v2 明确 PydanticAI 作为执行引擎：

# v2: AgentRunEngine 委托给 PydanticAI
class AgentRunEngine:
    def __init__(self, llm_runtime: LLMRuntime, tool_registry: ToolRegistry, ...):
        self.llm_runtime = llm_runtime
        self.tool_registry = tool_registry

    async def run(self, user_input: str, context: AgentContext) -> AgentRunResult:
        # 构建 PydanticAI Agent（动态注入工具）
        agent = PydanticAgent(
            model=OpenAIModel(context.model, base_url=...),
            system_prompt=self._build_system_prompt(context),
            tools=self._resolve_tools(context.tools, context.workspace_id),
        )
        # PydanticAI 处理 tool call 循环、结构化输出、重试
        result = await agent.run(user_input, deps=context)
        return AgentRunResult(...)

3.3 工具系统 (MCP + PydanticAI)

与 v1.0 一致，v2 追加：

  • 执行时权限校验：ToolExecutor 在每次调用前重新校验 User/Workspace 对该工具+参数的权限
  • Argument-Level 策略检查：不仅检查工具级别，还检查参数级别（如 content_type 是否在允许列表）
  • Prompt Injection 防护：Tool handler 接收的 context 对象区分 context.user_content（不可信的 CMS 内容）和 context.system_instruction（可信的开发者 prompt）
  • Correlation ID 传递：每个 tool call 携带 correlation_id

3.5 人工审批与护栏 v2 新增

破坏性操作审批流程

Agent 决定执行写操作
  │
  ├─→ 1. Dry-Run: 生成操作预览（将要创建/修改的内容 diff）
  │
  ├─→ 2. 用户审批: 前端展示 diff → 用户 Approve / Reject / Modify
  │     (Phase 3B 初期: 必须人工审批。后期: 可配置自动化策略)
  │
  ├─→ 3. 执行: 审批通过后，以用户身份执行操作
  │     (携带审批记录 ID，写入审计日志)
  │
  └─→ 4. 回执: 操作结果计入 Agent Session

审批策略配置 (Phase 3B+):
  - always_approve:      所有写操作需审批
  - approve_bulk_only:   单条写入自动；批量(>5)需审批
  - approve_schema_only: 内容写入自动；Schema 变更需审批
  - auto_approved:       白名单内的自动化 Agent 可自动执行
                         (仅限特定内容类型 + 特定操作)

附录 A2. 术语表

与 v1.0 一致，v2 追加术语：

术语定义
Tenant-Aware Registry每个 Registry Consumer 在请求时接受 workspace_id + user_id + activation_revision 进行租户感知解析，而非启动时全局注册。
Activation Revisionworkspace_extensions 的单调递增版本号。每次 activate/deactivate/config_update 时递增，用于缓存失效。
Trusted Extension第一方或认证第三方 Extension，加载进 API 进程。通过 Permission 声明 + 审计日志 + API Client Facade 防止意外越权。
Untrusted ExtensionMarketplace/Community Extension。需要进程/容器/WASM 隔离 + RPC boundary。当前路线图不支持（独立项目）。
LLMRuntimeLLM 调用高层入口。集中管理 Key 解析、审计、预算预检查、模型策略强制。调用方不需要自行传递 virtual_key_id。
Correlation ID跨系统追踪标识符。贯穿 HTTP Request → Agent Session → LiteLLM Request → Tool Call → Extension Audit → Background Task。
Dry-RunAgent 写操作在执行前生成操作预览/diff，供用户审批。不实际修改数据。
Approval WorkflowAgent 破坏性操作需人工审批后才能执行。支持审批/拒绝/修改。可配置审批策略（始终/批量/Schema变更/自动）。
